  PARTIE 1 — RÉSUMÉ DES RÔLES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

L'application utilise un système de rôles hiérarchique à 3 niveaux, défini dans
backend/config/packages/security.yaml.

Hiérarchie (du plus bas au plus élevé) :
  ROLE_USER  <  ROLE_REDACTOR  <  ROLE_ADMIN

Un rôle supérieur hérite automatiquement de tous les droits des rôles inférieurs.

──────────────────────────────────────────────────────────────────────────────
  RÔLE 1 : ROLE_USER (utilisateur standard)
──────────────────────────────────────────────────────────────────────────────
Attribué par défaut à tout utilisateur inscrit.

Permissions :
  ✔ Consulter les ressources visibles (articles, contenus)
  ✔ Pratiquer les exercices de respiration
  ✔ Marquer des ressources comme lues
  ✔ Ajouter/retirer des ressources en favoris
  ✔ Consulter son activité personnelle (/api/me/activity)
  ✔ Modifier son profil (/api/me)
  ✔ Supprimer son propre compte (/api/me DELETE)

Restrictions :
  ✘ Créer ou modifier des ressources
  ✘ Créer des exercices de respiration
  ✘ Accéder au panneau d'administration
  ✘ Gérer les autres utilisateurs

──────────────────────────────────────────────────────────────────────────────
  RÔLE 2 : ROLE_REDACTOR (rédacteur de contenu)
──────────────────────────────────────────────────────────────────────────────
Attribué manuellement par un administrateur.

Hérite de : ROLE_USER (tous ses droits)

Permissions supplémentaires :
  ✔ Créer de nouvelles ressources (POST /api/resources)
  ✔ Modifier ses propres ressources (PUT /api/resources/{id})
  ✔ Supprimer ses propres ressources (DELETE /api/resources/{id})

Restrictions :
  ✘ Modifier les ressources d'autres auteurs
  ✘ Créer des exercices de respiration
  ✘ Accéder au panneau d'administration
  ✘ Gérer les utilisateurs

──────────────────────────────────────────────────────────────────────────────
  RÔLE 3 : ROLE_ADMIN (administrateur)
──────────────────────────────────────────────────────────────────────────────
Rôle le plus élevé, attribué manuellement.

Hérite de : ROLE_REDACTOR + ROLE_USER (tous leurs droits)

Permissions supplémentaires :
  ✔ Accéder au tableau de bord EasyAdmin (/admin)
  ✔ Créer, modifier et supprimer des exercices de respiration
  ✔ Supprimer n'importe quelle ressource (y compris celles des autres)
  ✔ Gérer la visibilité des ressources (toggle visible/invisible)
  ✔ Consulter les statistiques de l'application
  ✔ Gérer tous les utilisateurs via l'interface d'administration
  ✔ Modifier les rôles des utilisateurs

──────────────────────────────────────────────────────────────────────────────
  Implémentation technique
──────────────────────────────────────────────────────────────────────────────
Fichier principal : backend/src/Entity/User.php

  - Les rôles sont stockés en base de données dans un champ JSON (array PHP)
  - La méthode getRoles() ajoute automatiquement ROLE_USER si absent
  - La hiérarchie est gérée par Symfony Security (pas de logique custom)
  - Les contrôleurs utilisent l'attribut PHP #[IsGranted('ROLE_X')] pour protéger
    les routes critiques

Extrait de code (User.php) :
  public function getRoles(): array
  {
      $roles = $this->role;
      $roles[] = 'ROLE_USER'; // garanti pour tous les utilisateurs
      return array_unique($roles);
  }

Configuration security.yaml :
  role_hierarchy:
      ROLE_ADMIN: [ROLE_REDACTOR]
      ROLE_REDACTOR: [ROLE_USER]

  PARTIE 2 — CONFORMITÉ RGPD
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Le RGPD (Règlement Général sur la Protection des Données) impose plusieurs
obligations aux applications traitant des données personnelles d'utilisateurs
européens. Voici l'état de conformité de CesiZen.

──────────────────────────────────────────────────────────────────────────────
  POINTS CONFORMES ✔
──────────────────────────────────────────────────────────────────────────────

1. DROIT D'ACCÈS AUX DONNÉES (Art. 15 RGPD)
   L'utilisateur peut consulter toutes ses données personnelles via :
   - GET /api/me → retourne email, prénom, nom, rôle
   - GET /api/me/activity → retourne :
       • Ressources lues (titre, type)
       • Ressources favorites (titre, type)
       • Exercices complétés (nom, type, durée)

   Fichier : backend/src/Controller/Api/AuthController.php

2. DROIT À L'EFFACEMENT / DROIT À L'OUBLI (Art. 17 RGPD)
   L'utilisateur peut supprimer son propre compte à tout moment :
   - DELETE /api/me → suppression complète de l'entrée en base de données
   - Toutes les données liées (favoris, lectures, exercices) sont supprimées
     par cascade

   Fichier : backend/src/Controller/Api/AuthController.php
   Méthode : deleteMe()

3. VÉRIFICATION DE L'EMAIL / CONSENTEMENT À L'INSCRIPTION (Art. 7 RGPD)
   - À l'inscription, un email de vérification est envoyé via un lien signé
   - Le compte est marqué isVerified = false jusqu'à confirmation
   - Cela garantit que l'utilisateur a consenti en contrôlant son adresse email

   Fichier : backend/src/Security/EmailVerifier.php
   Bundle  : symfonycasts/verify-email-bundle v1.18

4. MINIMISATION DES DONNÉES (Art. 5 RGPD)
   Seules les données nécessaires au fonctionnement sont collectées :
   - Prénom, nom, email, mot de passe hashé
   - Aucune donnée de géolocalisation, numéro de téléphone, ou donnée
     sensible n'est collectée

5. TRAÇABILITÉ (horodatage) (Art. 5 RGPD - intégrité)
   Toutes les entités disposent de timestamps automatiques :
   - createdAt : date de création
   - updatedAt : date de dernière modification
   Via le trait Gedmo\TimestampableEntity

──────────────────────────────────────────────────────────────────────────────
  POINTS MANQUANTS / AXES D'AMÉLIORATION ✘
──────────────────────────────────────────────────────────────────────────────

1. BANDEAU DE CONSENTEMENT AUX COOKIES (Art. 7 RGPD)
   ✘ Aucun bandeau cookie ni gestion du consentement n'est implémenté côté
     frontend. Si des cookies analytiques ou de tracking sont utilisés,
     le consentement explicite est obligatoire.

2. EXPORT DES DONNÉES (Art. 20 RGPD - Portabilité)
   ✘ L'endpoint /api/me/activity retourne les données mais pas dans un format
     exportable standard (JSON téléchargeable, CSV, etc.).
     À implémenter : un bouton "Exporter mes données" au format JSON/CSV.

3. POLITIQUE DE CONFIDENTIALITÉ (Art. 13 RGPD)
   ✘ Aucune page ou endpoint de politique de confidentialité n'est présent.
     Il faut informer l'utilisateur sur : qui traite ses données, pourquoi,
     combien de temps, et ses droits.

4. ANONYMISATION (alternative à la suppression)
   ✘ La suppression de compte efface complètement les données. Une option
     d'anonymisation (remplacer email/nom par des valeurs neutres) pourrait
     être préférable pour conserver les statistiques d'usage.

5. JOURNALISATION DES ACCÈS AUX DONNÉES (Art. 30 RGPD)
   ✘ Aucun journal d'audit ne trace qui a accédé à quelles données
     et à quelle heure.

6. DURÉE DE CONSERVATION (Art. 5 RGPD)
   ✘ Aucune politique de rétention des données n'est définie.
     Les données sont conservées indéfiniment tant que l'utilisateur ne
     supprime pas son compte.

──────────────────────────────────────────────────────────────────────────────
  Bilan RGPD
──────────────────────────────────────────────────────────────────────────────
  Droits couverts  : Accès (Art.15) ✔ | Effacement (Art.17) ✔ | Minimisation ✔
  Droits partiels  : Consentement (Art.7) — uniquement email, pas cookies
  Droits absents   : Portabilité (Art.20), Politique de confidentialité (Art.13)

  Note globale : Base solide, mais une mise en conformité complète nécessite
  l'ajout d'une politique de confidentialité, d'un bandeau cookie et d'un
  export des données.

  PARTIE 3 — SÉCURITÉ DES DONNÉES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

CesiZen implémente plusieurs couches de sécurité. Voici le détail complet.

──────────────────────────────────────────────────────────────────────────────
  1. AUTHENTIFICATION PAR JWT (JSON Web Token)
──────────────────────────────────────────────────────────────────────────────
Fichier : backend/config/packages/lexik_jwt_authentication.yaml
Bundle  : lexik/jwt-authentication-bundle v3.2

  - Authentification STATELESS : aucune session côté serveur
  - Les tokens sont signés avec une paire de clés RSA (asymétrique)
      • Clé privée : /config/jwt/private.pem (pour signer)
      • Clé publique : /config/jwt/public.pem (pour vérifier)
      • Protégées par passphrase via variable d'environnement JWT_PASSPHRASE
  - Durée de vie du token : 3600 secondes (1 heure)
  - Le token doit être envoyé dans l'en-tête HTTP : Authorization: Bearer <token>
  - Après expiration, le client doit se reconnecter (pas de refresh token)

  Avantages : résistant aux attaques CSRF, scalable, adapté aux APIs REST

──────────────────────────────────────────────────────────────────────────────
  2. HASHAGE DES MOTS DE PASSE
──────────────────────────────────────────────────────────────────────────────
Fichier : backend/config/packages/security.yaml

  password_hashers:
      PasswordAuthenticatedUserInterface: 'auto'

  - L'algorithme 'auto' sélectionne le meilleur disponible (bcrypt ou argon2id)
  - Les mots de passe ne sont JAMAIS stockés en clair
  - Le hash est irréversible (one-way)
  - En environnement de test, coût réduit à 4 (pour la rapidité des tests)

──────────────────────────────────────────────────────────────────────────────
  3. PROTECTION CSRF (Cross-Site Request Forgery)
──────────────────────────────────────────────────────────────────────────────
Fichier : backend/config/packages/csrf.yaml

  framework:
      form:
          csrf_protection:
              token_id: submit

  - Tokens CSRF stateless pour les formulaires (login, logout, authenticate)
  - Protège contre les requêtes malveillantes depuis des sites tiers
  - L'API REST avec JWT est naturellement protégée contre CSRF (pas de cookies)

──────────────────────────────────────────────────────────────────────────────
  4. CONTRÔLE D'ACCÈS AUX ROUTES
──────────────────────────────────────────────────────────────────────────────
Fichier : backend/config/packages/security.yaml (section access_control)

  Routes publiques (sans authentification) :
    - POST /api/login
    - POST /api/register
    - GET  /api/resources (liste)
    - GET  /api/resources/{id} (détail)
    - GET  /api/breathing-exercices (liste)

  Routes protégées :
    - /admin/** → ROLE_ADMIN requis
    - /api/**   → IS_AUTHENTICATED_FULLY (JWT valide requis)

  Au niveau des contrôleurs, l'attribut #[IsGranted()] renforce les droits :
    #[IsGranted('ROLE_REDACTOR')] → sur la création de ressources
    #[IsGranted('ROLE_ADMIN')]    → sur les actions administratives

──────────────────────────────────────────────────────────────────────────────
  5. AUTORISATION AU NIVEAU MÉTIER (Business Logic)
──────────────────────────────────────────────────────────────────────────────
Fichier : backend/src/Controller/Api/ApiResourceController.php

  En plus des rôles, la propriété des ressources est vérifiée :

  $isAdmin  = in_array('ROLE_ADMIN', $user->getRoles());
  $isAuthor = $resource->getAuthor() === $user;

  if (!$isAdmin && !$isAuthor) {
      return $this->json(['message' => 'Access denied'], 403);
  }

  → Un rédacteur ne peut modifier/supprimer QUE ses propres ressources
  → Un admin peut tout faire

──────────────────────────────────────────────────────────────────────────────
  6. CONFIGURATION CORS (Cross-Origin Resource Sharing)
──────────────────────────────────────────────────────────────────────────────
Fichier : backend/config/packages/nelmio_cors.yaml

  nelmio_cors:
      defaults:
          allow_origin: ['http://localhost:5173']
          allow_methods: ['GET', 'OPTIONS', 'POST', 'PUT', 'PATCH', 'DELETE']
          allow_headers: ['Content-Type', 'Authorization']

  - Seul le frontend React (localhost:5173) est autorisé à appeler l'API
  - Bloque les requêtes depuis des origines non autorisées
  - À mettre à jour avec l'URL de production lors du déploiement

──────────────────────────────────────────────────────────────────────────────
  7. VALIDATION DES DONNÉES EN ENTRÉE
──────────────────────────────────────────────────────────────────────────────
Fichier : backend/src/Entity/User.php + backend/src/Form/RegistrationFormType.php

  Contraintes appliquées :
  - UniqueEntity sur l'email → pas de doublon possible
  - NotBlank sur les champs obligatoires
  - Length (min: 6, max: 4096) sur les mots de passe
  - IsTrue pour la validation des conditions d'utilisation

  Les contrôleurs API vérifient également les champs requis avant traitement
  et retournent des codes HTTP appropriés (400, 422).

──────────────────────────────────────────────────────────────────────────────
  8. SÉPARATION DES ENVIRONNEMENTS
──────────────────────────────────────────────────────────────────────────────
  - .env          → variables de production (non versionnées)
  - .env.test     → base de données séparée pour les tests
  - Les secrets (JWT_PASSPHRASE, DATABASE_URL) sont en variables d'environnement
    et non codés en dur dans le code source
